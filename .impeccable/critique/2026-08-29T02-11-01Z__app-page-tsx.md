## Design Specificity Verdict

**The skin is authored for this product. The information architecture is off the shelf. And the one thing that makes this not-MyFitnessPal is invisible on the primary surface.**

Genuinely product-specific: `Meter` as a 4px horizontal instrument scale rather than a ring (six fit in ~80px of vertical space — a real answer to a real portrait-phone constraint); the 16px `.gridlines` measurement grid marking exactly one panel as the instrument face; the `.num` mono/sans semantic split, enforced rather than declared; the per-100g `Product` model with grams inline next to the Log button, which encodes the actual label-photo workflow; the connector panel.

Category-interchangeable: the Today stack itself — week strip → hero number → macro grid → quick chips → collapsibles → meal-grouped list — is the Lose It / MyFitnessPal / Cronometer sequence unmodified. The bottom nav spends all four thumb-reachable slots on navigation and zero on capture, in a product whose stated success metric is capture speed. `TrendsCard` and `WeightCard` are a visibly earlier app: `p-5` padding and `mb-4` gaps against a system whose largest gap is 8px, `text-sm` sentence-case headings, `text-3xl` weight display, and a `bg-accent text-white ... active:scale-[0.98]` button that breaks the One Signal Rule, the Float-Only Rule and the flat-on-interaction rule in a single line.

## Overall Impression

The visual system is the strongest thing here and it is not the problem. The problem is that this is an app which **cannot be trusted to be showing you the truth**, in a product whose entire value is a trustworthy set of figures.

Two independent failures produce that: the Today screen never refetches after mount, so anything Claude logs is invisible until a hard reload; and one-tap logging inherits its meal type from a `<select>` hidden inside a collapsed panel that defaults to breakfast and never follows the clock. The first breaks the dual-path positioning at the structural level. The second corrupts the app's single best interaction for most of the waking day. Both are cheap to fix.

The single biggest opportunity is smaller than either: the seven-day strip occupies prime real estate at the top of the primary screen and carries **zero data** — a weekday letter and a date. Give each cell a hairline goal-state mark and the strip becomes the completeness instrument this product has no representation of, delivering "the day is recorded" feedback with no praise, no streak, and no new colour.

## What's Working

**1. `Meter` is the right component, and it earns the density claim.** A ring at readable size costs ~90px square; six meters cost ~80px total including panel padding. It reads left-to-right like a scale, `value/goal` is one tabular string, and the value alone bolds and turns red on overage while the label holds — so overage is legible peripherally without a colour explosion. A considered answer to six nutrients on a portrait phone, not a styling choice.

**2. The mono/sans split is enforced, not decorative.** `.num` appears on the calorie total, strip dates, entry calories, the P/C/F triplet, the timezone string and the connector URL — and nowhere on prose. Because it is honoured consistently, "is this a measured thing?" is answerable pre-attentively. Most systems declare this rule; this one applies it.

**3. The `Product` + grams model encodes the real workflow.** Per-100g storage scaled at log time means a label is read once ever, and the grams field sits in the row beside the Log button — pick, adjust, tap, no modal. `productId`/`quantityGrams` on the entry, surfaced as a grams badge in `EntryRow`, keeps a scaled entry auditable afterwards. The product thesis, working.

## Priority Issues

### [P0] The Today screen never refetches, so Claude's entries are invisible and get double-logged
**What:** `loadDay` runs only on `[ready, date]` (`page.tsx:144-146`). Verified: no `visibilitychange` listener, no focus revalidation, no polling, no refresh control anywhere. Tab switches don't refetch (`tab` isn't a dependency), and an installed standalone PWA isn't remounted when resumed from background.
**Why it matters:** This is the structural failure of PRODUCT.md's core positioning and Principle 2 ("Two front doors, one truth"). Log via Claude, open the installed app: it shows the pre-Claude day, indefinitely. Seeing the meal missing, you log it again. The one differentiating claim produces duplicate records and an untrustworthy day.
**Fix:** Add a `visibilitychange` + `focus` effect calling `loadDay(date)` and `api.listFavorites()`. Put a `.num` last-loaded timestamp in the calorie panel header, tappable to reload. Re-evaluate `todayStr()` on visibility so midnight rollover advances `date`. Longer term add a `source` column to `FoodEntry` — the schema currently cannot distinguish the two paths at all.
**Suggested command:** `/impeccable harden`

### [P0] Quick-add and product logging silently file into the wrong meal
**What:** `selectedMeal={form.mealType}` (`page.tsx:357`) and `defaultMeal={form.mealType}` (`page.tsx:369`) read a `<select>` inside the collapsed "Add food" panel that initialises to `"breakfast"` (`page.tsx:58`) and never changes with time of day. `QuickAdd` (`QuickAdd.tsx:32`) shows no indication of the target meal.
**Why it matters:** It corrupts the one-tap path — the app's fastest and best interaction — for most of the waking day, and correction is expensive because delete is invisible on touch. A silently-wrong log is worse than a hard one.
**Fix:** Decouple. Derive a default from local time (`<10:00` breakfast, `<15:00` lunch, `<21:00` dinner, else snack), hoist it to a visible 4-segment control directly above the quick-add chips, and have the Add-food select mirror that shared state rather than own it. The chip row then reads its target at a glance.
**Suggested command:** `/impeccable clarify`

### [P1] Delete is invisible on the device the product is designed for, and nothing is undoable
**What:** `EntryRow.tsx:129` — `opacity-0 ... group-hover:opacity-100`. Touch has no hover, so the control is permanently invisible while remaining in the layout and tappable at roughly 11×14px. No delete anywhere confirms or offers undo; `removeEntry` (`page.tsx:197`) has no error handling.
**Why it matters:** Correcting a wrong entry is the second-most-common action in a tracker. It is currently a hidden, mis-tappable target with an irreversible outcome — while `regenerateKey`, a once-a-year action, gets the app's only confirmation dialog.
**Fix:** Make `✕` always visible at `--ink-faint` with a 44×44 hit area. Replace confirm-free deletion with optimistic removal plus an "Entry deleted · UNDO" toast (give the toast system an action slot). Apply to favorites, products, templates and weight logs, and wrap all seven unguarded mutations in `try/catch`.
**Suggested command:** `/impeccable harden`

### [P1] The zero state renders as a broken instrument and offers no way out
**What:** With all goals `null`, the calorie readout renders an 8px track at permanent 0% (`page.tsx:331`) and all six meters render 4px tracks at 0% (`Meter.tsx:47`) — seven full-width empty rails, the exact visual signature of "you have eaten nothing," even after three logged meals. The entries empty state names favorites and products, both of which are empty, and `QuickAdd` is unmounted entirely (`page.tsx:352`) so two of its three named routes aren't on screen. Nothing anywhere prompts goal-setting. `WeightCard` has four independent guards and no fallback copy at all — a new user sees a header and a form.
**Why it matters:** This is precisely what PRODUCT.md's "handful of invited friends" meet on day one. The screen reads as malfunctioning rather than unconfigured, and a tracker with no targets is the product removed.
**Fix:** When `goal == null`, suppress the rail entirely and replace the `value/goal` string with a right-aligned 11px `SET GOAL` link. On the calorie panel, swap the empty bar for a hairline rule plus `NO GOAL SET · CALCULATE` wired to `TdeeCard`. Make the entries empty state name only routes that exist for this user. Give `WeightCard` a real empty state.
**Suggested command:** `/impeccable onboard`

### [P1] The 11px annotation layer fails AA in both themes, with pinch-zoom disabled
**What:** Computed: `--ink-faint` is **3.18:1** on `--panel` light, **3.07:1** dark, **2.74:1** on `--bg` light. It carries every label, unit, count, hint and placeholder in the app, at 11px (`text-2xs`) or 12px — never large-text sizes, so 4.5:1 is the applicable threshold everywhere. `layout.tsx:22` sets `userScalable: false, maximumScale: 1`, removing the user's ability to compensate. Separately `Toast.tsx:37-39` hardcodes `text-white`: in dark, white on `--accent` `#f59e0b` is **2.15:1** and white on `--over` `#f87171` is **2.77:1** — and toasts are the app's only confirmation that a log succeeded. `--accent` on `--bg` in light is **4.32:1**, marginally failing for the 11px inline actions.
**Why it matters:** PRODUCT.md names one-handed use in bright and dark environments as a functional requirement. Blocking zoom on an interface whose annotation layer sits at 11px and 3:1 is the compounding version of that failure.
**Fix:** Lift `--ink-faint` to ≈`#6b7484` light and ≈`#7d8797` dark — both clear 4.5:1 without touching the near-monochrome character. Remove `maximumScale`/`userScalable`. Give toasts token-based foregrounds (`--panel` on accent in dark, not `#ffffff`). Delete the `[&>option]:text-black` hack in 4 files and rely on the `color-scheme` already declared.
**Suggested command:** `/impeccable audit`

### [P2] Two traps: copy-day defaults to copying today onto itself, and grams-after-pick is a no-op
**What:** `copyFrom` initialises to `date` (`TemplatesCard.tsx:17`) and the input's `max={date}` permits it; verified that `app/api/entries/copy/route.ts` has no `from !== to` guard — it only checks `source.length === 0`. One tap duplicates the entire day, with no undo. Also verified: the copy route drops `productId`/`quantityGrams`, so copying a day silently strips provenance from every entry. In `FoodSearch`, `grams` is applied at `pick()` time, so changing it after choosing a result does nothing.
**Fix:** Default `copyFrom` to `shiftDate(date, -1)`, disable Copy when `copyFrom === date`, and reject `from === to` server-side. Carry provenance through copy and template-apply. Move the grams field into the filled Add form so it recalculates live, or disable it once a result is chosen.
**Suggested command:** `/impeccable harden`

### [P2] Most interactive controls are far below the touch-target floor
**What:** Computed from padding + line-height: `.btn` resolves to ~28px and `.field` to ~34px system-wide. Only the bottom nav (~60px) and the week strip (~46px) clear 44px. Failing: `EntryRow` name (~20px) and delete (~14px), the `+ fiber/sugar/sodium` toggle (~14px), `★ favorite` / `⬚ product` (~14px), `Panel` disclosure headers (~30px), QuickAdd chips (~16-24px) and their `×` remove (~14px), `ProductsCard` delete (~14px), `WeightCard` delete (~16px), `ThemeToggle` and `TrendsCard` segments (~22px). A mis-tap on a favorite chip hits a 14px `×` that deletes it with no confirmation. *(Arithmetic from source; exact rendered values need a device.)*
**Fix:** Raise `.btn` and `.field` vertical padding to reach 44px, and give bare glyph buttons padding or `::before` hit-area expansion rather than resizing the glyph — the visual language stays dense while the targets don't.
**Suggested command:** `/impeccable adapt`

## Persona Red Flags

**Alex — the owner, one-handed at the counter.** Opens at 08:10 to log oatmeal already logged via Claude at 07:55; sees yesterday's totals because nothing refetched, logs it twice (`page.tsx:146`). Opens at 20:30, taps the "chicken thighs" recent chip, it files under **breakfast** (`page.tsx:357`). Fixing it means discovering the row is tappable, opening an undocumented editor, changing a select, saving — four taps and a discovery to undo one tap. His daily oatmeal chip has sunk to position ~14 in a hidden-scrollbar row by afternoon, because ordering is recency not frequency. Wanting a lunch from 9 days ago, he finds the strip only goes back 6 and the date input only materialises *after* he's already left today (`page.tsx:276`).

**Sam — the invited friend, day one, everything empty.** Explicitly in PRODUCT.md's confirmed direction, and the app is not built for him. Lands on Today: a `0`, seven empty rails that read as broken rather than unset, `0 entries`. The empty-state copy names favorites and saved products; neither exists and the QuickAdd block is unmounted so he can't tell what a favorite even is. Opens "Products" (hint: "Saved labels") and is told to photograph a label and ask Claude — he has no connector and doesn't know what that means. In "Add food" he meets `kcal P C F`, types 320, watches the label vanish, leaves P/C/F blank; they save as `0` (`page.tsx:159-164`), so his protein meter reads `0g` forever with no signal it's missing rather than zero. Nothing ever tells him to set a goal.

**Riley — 43, presbyopic, bright kitchen, wet fingers.** Pinches to zoom the 11px labels; nothing happens (`layout.tsx:22`). In daylight the entire annotation layer sits at 3.18:1 — the figures are legible, everything explaining them is not. Every button is ~28px and every input ~34px. Taps a favorite, misses, hits the adjacent ~14px `×`, and the favorite is gone with no confirmation and no undo — and if the request failed, it vanishes from the UI anyway and returns tomorrow.

## Minor Observations

- `Panel` has no `aria-expanded`; week-strip buttons have no `aria-pressed`/`aria-current`; `BottomNav` has no `aria-current`. `ThemeToggle` and `TrendsCard` do this correctly — the pattern exists, it just wasn't applied on the main page.
- `TemplatesCard.tsx:80` — the copy-from date input has `outline-none` with no paired focus style, unlike its twins in `FoodSearch` and `WeightCard`. Zero visible focus indicator for keyboard users.
- `.btn` is defined after `@tailwind utilities` and outside `@layer`, so `ProductsCard.tsx:121`'s `btn btn-primary px-2 py-1` override is dead — `.btn`'s own padding wins the cascade.
- `date` is initialised once at mount (`page.tsx:92`) while `weekEnding(todayStr())` recomputes every render; after midnight the two disagree and nothing looks wrong.
- `consumedAt` is always local noon (`page.tsx:166`), so intra-meal ordering is arbitrary and "when did I eat this" is unrecoverable.
- `EntryRow.save()` omits `productId`/`quantityGrams`, so editing a product-logged entry leaves a grams badge that no longer matches the macros.
- `ProductsCard` is mounted twice (Today and Settings), each running its own debounced fetch; the Settings instance still shows the Today-oriented empty copy.
- `ProductsCard.tsx:148` — `{MEALS.length === 0 && null}` is dead code.
- `TemplatesCard.tsx:41` uses a native `prompt()`, which is blocked outright in some standalone PWA contexts.
- **No service worker exists** — `public/` holds only two icons. An installed home-screen app that shows the browser's offline page in a kitchen with bad wifi is a direct hit on "sustained logging."
- On mount, 9 API calls fire regardless of active tab; every single-item mutation refetches the whole day (`loadDay` = 2 calls), and `updateEntry` does an optimistic local update *and then* the redundant refetch.
- DESIGN.md's Don'ts still name `ThemeToggle` and `AuthForm` as current violations; both were fixed earlier this session, so those two bullets are now stale.

## Questions to Consider

1. The week strip is seven cells of prime real estate carrying zero data, in a product whose principle is "numbers are the content." What if each cell showed the day's goal state — a hairline fill, a 2px tick — so the strip became the completeness instrument the product currently lacks, without one word of praise?
2. PRODUCT.md says entries from both paths must be "indistinguishable in the day's record," *and* that each path should make the other's work "easy to see." Those pull against each other, and the code resolved it by doing neither. What if the *arrival* were visible ("3 entries added since you last looked") while the entries themselves stayed identical?
3. Four bottom-nav slots, all navigation, in the only guaranteed thumb-reachable region — on a product whose success metric is capture speed. What happens if one becomes a log action?
4. All six macro meters are weighted identically, but protein is consulted daily and sodium approximately never. What if the grid ordered by what actually has a goal, collapsing unset ones to "3 nutrients untracked," so it shrank to fit the user rather than the schema?
5. The app has no concept of "this day is done." If the failure mode it exists to prevent is the abandoned half-day, why is there no state for its opposite — and could that state be pure report (`4 MEALS · 1,840 KCAL · CLOSED`) rather than encouragement, which the brand correctly forbids?
