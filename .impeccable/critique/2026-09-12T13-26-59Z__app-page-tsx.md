## Overall Impression

This feels like an unusually intentional personal tool: calm, non-judgmental, technically honest, and built for fast repetition. The biggest opportunity is to make the moment where a user states nutrition data's basis unmistakable, without softening the application's disciplined terminal-readout character.

## What's Working

- **The visual system has conviction.** Hairline panels, tabular numerals, flat separation, controlled radius, and the single amber signal stay coherent in light and dark states.
- **The primary food flow respects actual use.** A large `Log food` entry point precedes analysis; repeat items can be logged with a tap and undone immediately.
- **Data integrity is visible.** Provenance, compatible units, scaled previews, preserved drafts, and UI/MCP parity help users verify rather than merely trust the record.

## Priority Issues

### [P1] Manual nutrition basis is too subtle

**What:** `Numbers are for this portion` and `+ Use a per 100 label` make a high-stakes operating mode look like optional advanced help.

**Why it matters:** Choosing the wrong basis misstates every nutrient and calorie, directly undermining the product's trustworthy-record promise.

**Fix:** Put a compact, square segmented control directly below Food: `AS EATEN` / `PER 100 G` (switching to ML when relevant). Reveal Amount and Unit only for the label mode; retain the existing preview.

**Suggested command:** `$impeccable clarify`

### [P2] Quick Add can file a past-day correction into the wrong meal

**What:** Quick Add writes immediately to the meal derived from the current clock, even while the user is viewing a historic day.

**Why it matters:** The meal is visible in subordinate text, but an interrupted user correcting breakfast at night can place the entry in snack and only recover through Undo.

**Fix:** Keep today truly one-tap. For a past day, foreground a compact `Quick-add to: [meal]` chooser before logging; the four meal options are a manageable decision.

**Suggested command:** `$impeccable harden`

### [P2] The closed Quick Add rail hides the repeat inventory

**What:** The phone view clips the next food chip with no visible scroll affordance; the composer search is not available until after a separate tap.

**Why it matters:** Habitual logging should make the user's common foods easy to recognize, not require them to remember that more choices sit off-screen.

**Fix:** Add a compact persistent `Search foods` affordance that opens the composer focused with its query preserved, and apply the existing edge-fade treatment to signal horizontal overflow. Do not add more chips or explanatory copy.

**Suggested command:** `$impeccable layout`

## Persona Red Flags

### Alex — power user

- Keyboard accelerators exist, but their reference is hidden in a closed Settings panel; Alex has to remember `?` before knowing shortcuts exist.
- Batch logging lives inside the expanded composer, so a repeat user cannot discover it from the default food dashboard.

### Jordan — first-timer

- The main Log Food action is clear, but manual entry asks Jordan to infer `portion total` versus `per 100` from subtle copy.
- Portion-mode help is stored in Settings instead of appearing where the form's behavior changes.

### Casey — distracted mobile user

- 44px targets, bottom navigation, and retained drafts are strong. The risk is rapid logging to a clock-derived meal while correcting a past day.
- A cropped, scrollbar-free quick-add rail makes it easy to miss a common item and fall back to one-handed typing.

## Cognitive Load and Emotional Journey

The interface has **moderate cognitive load (2 checklist failures)**. It passes on single focus, grouping, hierarchy, and progressive disclosure. The exceptions are a seven-day rail (a reasonable temporal-control exception), multi-source food search, and the seven-field fully expanded manual form; the more serious failure is working memory around whether values are per portion or per 100.

Emotionally, arrival feels calm and competent rather than congratulatory. Quick add creates a satisfying low-friction repeat moment. Manual label entry creates the only real valley because responsibility rises while the data model becomes less explicit. The existing preview and Undo restore confidence after completion, but should not carry the whole prevention burden.

## Minor Observations

- Keeping the desktop layout intentionally narrow and phone-like correctly honors the installed-PWA operating context.
- The dark-mode Log Food slab is visually assertive but works as a clear primary action; validate it with real users before weakening it.
- Normalize raw API failures into task-language recovery messages before treating them as primary feedback.

## Questions to Consider

- Should a past-day correction deliberately trade one tap for an explicit meal while today remains truly one-tap?
- If label entry is common, should nutrition basis become the first decision in the form rather than an advanced-looking link?
- What is the smallest persistent affordance that makes foods beyond four Quick Add chips discoverable without turning the dashboard into a search screen?
