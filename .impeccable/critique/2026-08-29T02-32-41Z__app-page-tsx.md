## Priority Issues

### [P0] The `.hit` helper collides at both call sites — a mis-tap deletes the favorite you meant to log
**What:** `.hit::after` (`globals.css:81-92`) is a 44×44 absolutely-positioned box centred on the glyph, with no `pointer-events: none`, on a `position: relative` parent — so it paints above non-positioned siblings and intercepts their taps. At `QuickAdd.tsx:77` the `×` sits inside a chip that is `py-1` (~24px tall) with the log button immediately to its left; the projected box overhangs roughly 18px onto that log button and ~10px above and below the chip. At `EntryRow.tsx:131` rows are `py-1.5` (~32px pitch) against 44px targets, so adjacent delete zones overlap by ~12px.
**Why it matters:** deleting a favorite has no undo and no confirm. The single fastest capture path in the product can silently destroy the thing being captured. Entry deletion has undo, so the row-overlap is milder, but still fires the wrong row.
**Fix:** `.hit` is the wrong shape for this. Either clamp the expansion to the parent's own height (never exceeding the row/chip pitch) and grow only horizontally, or drop `.hit` and separate the destructive control from the primary one — move remove-favorite behind a long-press or an explicit edit mode. Either way, add an Undo action to `deleteFav`; `Toast.tsx` already supports it.
**Suggested command:** `/impeccable adapt`

### [P1] A brand-new account still gets a fully-instrumented screen reporting nothing, with no path to goals
**What:** Unchanged — deliberately out of scope last pass. `calGoal` null ⇒ the `/goal` and `left`/`over` spans are suppressed (`:465-480`) and the 8px bar renders as a full-width empty track (`:483-494`); each `Meter` renders an empty 4px track (`Meter.tsx:229-240`). The week strip correctly suppresses its rail — and **the reasoning is written in the code at `:392-393`, then not applied to the calorie bar or the six meters.** `QuickAdd` is hidden entirely, and `:659` names a favorite and a saved product the user does not have.
**Fix:** make "unset" a state the system has a token for rather than something each component decides. Replace empty tracks with an explicit `Set a goal →` into Settings, and make the entries empty-state copy conditional on what exists.
**Suggested command:** `/impeccable onboard`

### [P1] The two moments that most demand verification show seven unlabeled boxes of digits
**What:** `EntryRow.tsx:64-87` and `page.tsx:576-586` rely entirely on `placeholder` for labels, and a populated field has no placeholder. So correcting a bad entry, and reviewing what Open Food Facts returned via `fillFromSearch` — which explicitly toasts "review & add" — both present identical right-aligned numeric fields with no way to tell carbs from fat. `Na` in edit mode vs `Na mg` in the add form label the same field differently.
**Fix:** persistent 11px uppercase labels above each numeric field, exactly as `GoalsCard.tsx:165-177` already does. Costs 14px of height in two places, and makes the add form consistent with the goals form.
**Suggested command:** `/impeccable clarify`

### [P1] The two co-equal paths produce a scrambled, timeless day
**What:** every UI entry is stamped `consumedAt` at local noon (`:231`, `QuickAdd.tsx:173`) while MCP entries carry real times, and the API orders by `consumedAt desc`. A Claude-logged 8am coffee therefore sorts above a UI-logged 8pm dinner, and all UI entries tie at noon leaving intra-group order to SQLite. No entry displays a time at all, so the ordering is unexplainable and unfixable by the user. PRODUCT.md asks each path to make the other's work "easy to see, verify and correct" — `revalidate` made the *data* visible; nothing makes the *change* visible.
**Fix:** stamp UI entries with the actual current time when `date === todayStr()` (noon is only a sane fallback for backdated logs), and show `HH:MM` per row in faint `.num`.
**Suggested command:** `/impeccable harden`

### [P2] Weight and Trends never went through the redesign
**What:** `p-5`/`mb-4` against the system's 12px/8px rhythm, `text-3xl` outside the type scale, a hand-rolled input (`WeightCard.tsx:379`), `bg-accent text-white` (2.15:1 in dark — the identical pair fixed in `Toast.tsx` this pass), `active:scale-[0.98]` against the documented no-transform rule, and 22px segmented controls. Neither has an empty state. Additionally `WeightCard.tsx:59` colours the weight delta `text-ok` when down and `text-warn` when up — **the app editorialising on the direction of a number**, wrong for any user whose TDEE goal is gain, and a direct violation of DESIGN.md's "green and red are goal state only."
**Fix:** port both to `panel p-3`, `.field`, `.btn btn-primary` and 11px uppercase headers; add empty and error branches; make the delta `--ink-dim` regardless of sign.
**Suggested command:** `/impeccable polish`

### [P2] Tab and date are React state, not route
**What:** neither `tab` (`:101`) nor `date` (`:107`) touches the URL. Android back exits the PWA from any tab; there is no deep link to a day or a tab; and switching tabs unmounts the Today subtree, resetting every `Panel`'s open state, `ProductsCard`'s query, `FoodSearch`, `TemplatesCard`'s `copyFrom`, and any in-progress edit. It also means the assistant — a co-equal front door — cannot link to anything it just changed.
**Fix:** move both to search params (`?tab=trends&d=2026-08-29`).
**Suggested command:** `/impeccable harden`

## Persona Red Flags

**The owner, one hand on a plate.** Unlocks, PWA opens, `revalidate` fires, totals are current — this now works. Then the favorite chip's log button is ~24px tall with its right edge overlaid by the delete's 44px hit box, so the fastest action in the app is the one most likely to mis-fire into an unrecoverable delete. Beyond the fourth favorite the row scrolls with no affordance saying so. Falling back to Products means tap-to-open, tap a 14px search field (which triggers iOS auto-zoom, since `.field` is 14px), type, then tap a 24px Log button.

**The invited friend, day one.** Registers, lands on Today, sees seven identical blank day cells, a `0` in 36px monospace with nothing after it, a full-width empty bar, six labels reading `0g` over empty rails, a meal selector already set to `lunch`, no quick-add section at all, three collapsed strips, and copy naming two collections they do not have. Nothing on the screen mentions that goals exist. The co-equal second front door is the last-but-one section of Settings, below Export, and assumes they already know what "Claude.ai → Connectors" means.

**The presbyopic evening user.** Pinch-zoom is preserved and deliberately so — the right call, now verified in `layout.tsx`. But the annotation layer is 11px and carries every unit, label and the whole `P/C/F` triplet; every numeric field is 14px so tapping one triggers an additional iOS auto-zoom; and `WeightCard`'s white-on-amber button is ~2.1:1 in dark. The reload button's `aria-label="Reload this day"` (`:449`) **overrides** its visible content, so a screen-reader user never hears the entry count or the sync time — the two facts the button exists to convey.

## Questions to Consider

1. **If the assistant is a co-equal front door, why can it not link to anything?** No tab, day, or entry has a URL. Claude can write to the day but cannot say "here, look." What would this interface be if `/?tab=today&d=2026-08-29#entry-abc` worked?
2. **Your own comment at `:392-393` explains why an empty rail is a lie when no goal is set. Why does that reasoning stop at the week strip?** Should "unset" be a token the design system owns, rather than something each component re-decides?
3. **`WeightCard.tsx:59` colours weight loss green and gain amber.** Is that a bug, or evidence that "we don't encourage" is easier to write in a document than to hold when a number has a direction?
4. **Every interactive primitive except the bottom nav and the week strip is 22–34px, and the one remedy built for it collides at both call sites.** Is 44px actually incompatible with "density is the virtue," or has density never been costed against the thumb it was designed for?
5. **The Today screen offers eight ways to log food; five are empty on a new account.** If you had to delete four, which four — and does that suggest the screen should be composed from what the user has rather than rendering all eight scaffolds unconditionally?
