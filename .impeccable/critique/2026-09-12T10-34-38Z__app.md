## Design Specificity Verdict

**LLM assessment:** The interface is visually authored for this product. Its week strip, tabular figures, hairline panels, calorie measurement grid, and restrained amber signal create a credible instrument rather than a generic wellness dashboard. The interaction architecture is less specific: generic disclosures, a Note/Cards split, inline forms that inflate list rows, and several unrelated overlay implementations feel accumulated rather than governed by one rule.

**Deterministic scan:** The detector returned two findings in `app/globals.css`: a two-axis grid background at line 81 and a font token warning at line 90. Both are contextual false positives. DESIGN.md explicitly permits the measurement grid behind the calorie readout, and Tailwind's resolved mono stack matches the documented typography exactly. There were **zero clearly actionable detector findings**.

**Visual overlays:** Browser mutation preflight failed: the title did not change and the injected script selector remained absent. No detector script was injected, and no reliable user-visible overlay exists. Browser screenshots, accessibility snapshots, element bounds, computed styles, and source inspection were used as fallback evidence.

## Overall Impression

The app already knows what it wants to look like, and it protects user data unusually well. Its main weakness is that focused work does not have a consistent spatial home: some tasks expand the page, some replace rows, some use ad-hoc sheets, and four existing dialogs behave differently. The biggest opportunity is a single responsive dialog/sheet contract, applied only where the user temporarily works on one object or confirms one consequential action.

## What's Working

1. **Numerical hierarchy is distinctive and legible.** The Today view puts the day's figures first and avoids generic wellness decoration.
2. **State safety is thoughtful.** Food and workout drafts, unit conversion, previews, import dry-runs, save telemetry, and Undo support trustworthy logging.
3. **The mobile foundation is sound.** Bottom navigation, safe areas, labelled controls, week navigation, and the narrow app column suit short one-handed sessions.

## Priority Issues

### [P1] Establish one accessible modal contract

**Why it matters:** Barcode Scanner traps and restores focus and locks page scroll; Shortcuts, Exercise History, and Workout Import do not. Add Exercise looks modal on a phone but has no dialog semantics. Background navigation and global shortcuts can remain active behind these overlays.

**Fix:** Build one shared responsive Dialog/Sheet primitive with initial focus, focus trap, focus restoration, body scroll lock or inert background, Escape handling, a labelled title, consistent backdrop, safe-area padding, an internal scroll region, and sticky actions. Derive it from Barcode Scanner's stronger focus lifecycle, then migrate existing overlays before adding new ones.

**Suggested command:** `$impeccable harden`

### [P1] Move bounded correction/composition tasks out of expanding rows

**Why it matters:** Editing a food entry replaces one compact row with up to ten fields; browser measurement put Save below the viewport and behind the fixed nav. The saved-product editor is similarly dense. Add Food combines discovery and detailed composition, making the page grow after selection.

**Fix:** Use a bottom sheet on phone and contained dialog on desktop for Entry Edit and Product Edit, with pinned Save/Cancel. For Add Food, preserve the fast discovery surface, then open **Confirm & Scale / Manual entry** in the task sheet after a selection or custom-entry action. Keep the draft when dismissed. This resolves the two independent reviews' only meaningful difference: it gains focus without putting the fastest browsing actions behind an unnecessary overlay.

**Suggested command:** `$impeccable shape`

### [P1] Remove the workout's second mental model and optional tail

**Why it matters:** Note and Cards are two representations of one record. Cards can become empty when the note does not parse and sends the user back to Note. The training-summary Details disclosure adds another optional branch to an already busy screen.

**Fix:** Remove Cards mode and the training Details control as requested. Preserve one canonical note workflow. Deliberately decide whether the Cards-only Set Complete and Add Set behaviors survive, while retaining exercise history and the rest timer. Keep the four summary metrics inline; do not move the removed muscle-group breakdown into a modal by default.

**Suggested command:** `$impeccable distill`

### [P2] Give rare irreversible actions real alert dialogs

**Why it matters:** Regenerating the API key disconnects every assistant, but its warning is squeezed into the timezone row. Deleting a workout removes the session and its local state without Undo, but confirmation is compressed beside mode/save controls.

**Fix:** Use compact alert dialogs for API-key regeneration and whole-workout deletion. Default focus to Cancel, name the affected item/date, state the consequence, disable backdrop dismissal, and reserve destructive styling for the final action. Keep food, meal, product, and weight deletions immediate because they already provide Undo.

**Suggested command:** `$impeccable harden`

### [P2] Make the macro grid deterministically two rows

**Why it matters:** `FoodTab.tsx` encodes `min-[480px]:grid-cols-6`, which requests the inconsistent one-row desktop layout. The live development CSS did not emit that utility and happened to render three columns, demonstrating a source/runtime mismatch rather than a reliable fix.

**Fix:** Use a stable three-column grid at all supported widths, producing two rows of three meters, and verify the computed column count or screenshot at desktop width.

**Suggested command:** `$impeccable adapt`

## Persona Red Flags

### Casey — distracted, one-handed mobile user

- Entry Edit and detailed Add Food composition can put Save/Log beyond a viewport while bottom navigation stays active.
- Add Exercise creates a second scrolling context with seven filters and dozens of choices.
- The retained drafts, meal selector, bottom navigation, and touch-size floor are strong foundations.

### Jordan — first-time user

- MCP, TDEE, per 100, Note/Cards, and parser error language assume prior knowledge.
- Cards appears to promise a simpler workout mode, then redirects back to Note when parsing fails.
- Repeated `Details +` labels conceal unrelated content: training analysis, connector risk, and export explanations.

### Sam — keyboard and screen-reader user

- Three declared dialogs lack the scanner's focus trap, focus restoration, and background isolation.
- Add Exercise is visually a sheet but lacks a dialog role, accessible name, and local Escape/focus contract.
- Workout and summary load failures can vanish without announced recovery.

## Minor Observations

- Existing modal backdrops vary from panel-colored blur to ink dimming to near-opaque fullscreen treatment.
- Workout Import occupies most of the mobile viewport even before a preview exists.
- The global day/tab shortcuts should be suspended whenever a modal is active.
- `Details +` is too generic to predict what it reveals.
- The detector found no actionable visual-system drift; the issues are interaction architecture, not palette or typography.

## Questions to Consider

- Should Add Food's boundary begin when users open food discovery, or only when they choose an item and begin Confirm & Scale? The evidence favors the latter.
- Which Cards-only capability is genuinely essential after Cards is removed: Set Complete, quick Add Set, both, or neither?
- Should TDEE become a modal in the first pass, or remain a Settings disclosure until the higher-impact editors and confirmations are standardized?
