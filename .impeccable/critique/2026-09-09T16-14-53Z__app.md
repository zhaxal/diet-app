## Design Specificity Verdict

The application is strongly authored for this product. The terminal readout, tabular figures, hairline panels, one amber signal, week-as-unit navigation, last-read timestamp, and equal UI/assistant entry model would not transfer unchanged to a generic wellness product.

The deterministic scan reported two findings in `app/globals.css`: `codex-grid-background` at line 81 and `design-system-font` at line 90. Both are false positives. The grid is limited to the calorie measurement surface and explicitly documented; `theme("fontFamily.mono")` resolves to the documented system monospace stack.

Browser inspection covered login, registration, Today, Trends, Weight, Settings, and API docs at 390×844 and 1440×900 in light and dark themes. No document-level horizontal overflow or console errors were found. Core mobile controls cleared 44px. Mutable overlay injection was unavailable, so screenshots, accessibility trees, computed dimensions, and console output were used.

## Overall Impression

The design is disciplined, fast, and trustworthy. The main opportunity is to keep the instrument density while removing cognitive and privacy friction from lower-frequency settings and sparse-data states.

## What's Working

1. Today follows the actual job: date context, current totals, meal destination, fast repeats, composer, and correctable entries.
2. Fast paths retain provenance and provide Undo rather than adding confirmation friction.
3. Offline and concurrent-writer states are explicit, timestamped, and recoverable.

## Priority Issues

### [P1] Settings exposes too many consequential controls at once

Daily goals and the optional TDEE calculator appear as back-to-back dense grids. Collapse the calculator as an optional task and use two columns at the narrowest supported widths.

### [P1] The connector credential is exposed by default

The full bearer URL appears in the accessibility tree and DOM. Mask it by default, retain one-tap Copy, provide deliberate Reveal/Hide, and state that the URL grants read/write access.

### [P1] Essential annotation text is strained in the primary mobile context

The 11px annotation layer passes AA contrast, but carries functional labels in a bright-kitchen, mid-life use case. Raise it to 12px for coarse pointers and narrow viewports while keeping the desktop instrument density.

### [P2] Sparse Trends overstates one day of evidence

One logged day creates a full chart and repeats the same value as min, median, and max. Present an insufficient-data state until at least two readings exist.

### [P2] Charts and Weight need stronger accessible labeling

Chart SVGs have no names, and Weight relies on placeholder text rather than a persistent visible field label. Add concise chart labels and a visible weight label.

### [P2] Inactive tabs fetch Trends and daily data unnecessarily

Every authenticated route currently requests the selected day, strip totals, and Trends even when the user opens Weight or Settings. Scope page-specific reads to the active tab.

### [P3] Auth footer links narrowly miss the 44px width target

The mobile Sign up and Log in links measure 42.6px and 34.3px wide. Give both a small inline padding while retaining the minimal auth layout.

## Persona Red Flags

**Alex, power user:** fast logging routes are strong; refreshes still pay for data from inactive tabs.

**Sam, accessibility-dependent user:** focus, names, contrast, and live regions are strong; unnamed charts and the exposed connector key weaken the path.

**Casey, distracted mobile user:** bottom navigation, drafts, and touch sizing are strong; dense Settings grids and tiny annotation text make one-handed correction harder.

**The self-hosting owner:** explicit freshness and assistant provenance build trust; a continuously visible bearer URL creates avoidable credential anxiety.

## Minor Observations

- Auth is visually consistent but could better state the product's two-entry-surface identity.
- The API reference uses an unpinned external Scalar runtime, conflicting with the documented self-contained deployment constraint.
- The API reference's third-party mobile controls include several targets below 44px.

## Questions to Consider

- Should calculated goals be a deliberate secondary task instead of a second always-visible form?
- Does the user ever need to read the connector URL, or only copy, reveal, and regenerate it?
- What should Trends say when it has a measurement but not yet a trend?

## Remediation Completed

- Daily Goals now uses two columns below 380px; the two-column TDEE form is an optional collapsed panel.
- Connector credentials are masked by default with explicit Reveal/Hide and read/write access copy.
- Phone annotation text is 12px and documented in `DESIGN.md` and the design sidecar.
- Nutrition charts wait for two logged days; chart SVGs have text alternatives; Weight has a persistent field label.
- Today, Trends, Weight, and Settings refresh only the data their active surface needs.
- Auth footer links clear the 44px touch target, and numeric Settings fields mirror server bounds.
- The API reference loads a pinned local Scalar bundle and adds mobile touch floors and visible keyboard focus.
