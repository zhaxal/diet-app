## Design Specificity Verdict

The capture half of this screen is authored for rationd and could not be lifted elsewhere. The reading half is a stock dashboard.

Product-specific and good: `⧉` copy writes nothing (trays the row, opens composer so amount is set first); `restateAmount` converts 241 g → 8.5 oz rather than reinterpreting "241"; quick-add ranking answers a different question at 08:00 than 19:00.

Generic, largest unspent opportunity: the six-meter macro grid gives all six nutrients identical grammar. Protein is a floor, carbs/fat are budgets, sugar/sodium are ceilings. `57/60g` sugar renders as a nearly-full amber progress bar — an achievement bar for eating sugar.

Sharpest irony: an app positioned on "two equally-supported front doors" expresses the second as an 11px grey `SRC: AI` string, no group-level cue, no explanation.

**Deterministic scan:** `impeccable detect` returned `[]`, exit 0, zero findings across eleven scoped files. Assessment B probed the engine with six planted violations and found it flags only 3 of 6 (hex literals, off-ramp font sizes, undeclared font families — not `rounded-full`, `shadow-lg`, or gradients). The clean result is real but narrower than it looks. The worst visual defect on this screen is invisible to it because the hex never appears in source — it comes from Tailwind preflight.

**Visual overlays:** none. Assessment B skipped the `live-server` + `detect.js` injection flow, so no user-visible overlay exists in the browser. Fallback signal is the measured evidence below.

## Overall Impression

Carefully built by someone who has used it. The composer's reference model is the best thinking in the codebase, and the a11y infrastructure beats most shipped commercial apps (63/63 focusable reachable, 0 unnamed controls, clean heading outline, working split live regions, 0 contrast failures in either theme, 0 console errors).

It has one bug that breaks the product's central constraint on the only device it's really used on, and one systemic theming defect that makes dark — the declared home ground — look wrong. Neither is a design problem. Both are cheap. The design problems underneath are real but second-order.

## What's Working

At 390×844 chip, display, goal bar and all six meters are above the fold together. The doc is stale; the code is right.

**The composer's reference model.** One segmented control whose label follows the unit's dimension; conversion on unit change rather than reinterpretation; `comparableUnits` refusing to invent a density; `portion`/`per`/`unitless`; sticky preview stating the row before it is written.

**The invisible infrastructure.** `Dialog` traps focus, sets `inert`, restores to trigger. `Toast` pauses on keyboard focus. `--ink-faint` carries a comment recording the measured ratios that forced it from `#8891a0` to `#636c7a`.

## Priority Issues

### [P0] Opening Trends at 30d pushes the entire bottom navigation off the phone screen

Measured at 390×844: collapsed 390/390 ✓; open 7d 390 ✓; **open 30d → scrollWidth 1375, nav width 1375, tabs at 352–576 / 576–800 / 800–1024**; open 90d 390 ✓; **open "all" → 1420, tabs at 374–598 / 598–822 / 822–1046**. All three tabs land outside the 0–390 window.

Root cause: coarse-pointer rule `app/globals.css:940-950` (`button { min-width: 44px }`) applies to the adherence strip's `flex-1` cells in `TrendsCard.tsx`, defeating flex shrink — 30 × 44 + 29 gaps = 1,349px in a 338px container, every ancestor `overflow-x: visible`. 90d escapes only because DESIGN.md's calendar fold kicks in past 92 days; the fold threshold was chosen against a ~20px desktop cell, never against the 44px touch floor.

Breaks PRODUCT.md constraint 3 and DESIGN.md's Reachable Nav Rule, two taps from the main screen, on a phone-first PWA. The touch-target fix caused it.

**Fix.** Lower the fold threshold so a flush row is used only when it fits (~7 cells at 390px), or exempt strip cells from the coarse `min-width`. Add `overflow-x: clip` on the panel as a guard. → `/impeccable adapt`

### [P1] The open composer presents the same two controls twice, 100px apart, inside one border

`FIND FOOD` filter → `RECENT` strip → `LOGGING TO / Dinner` + Select → second search field + barcode → `RECENT · 1 TAP` → second chip strip, same foods, different layout → `ENTER FOOD MANUALLY`. Meal stated twice within 60px, pickable in a third place.

The two fields do different things — filter-and-log-in-one-tap vs reach-catalog-and-fill-a-form — and nothing says so. This is the surface reached when the fast path already failed. It re-creates inside one panel the duplication DESIGN.md records collapsing three panels to fix.

**Fix.** Suppress the `QUICK ADD` block when `showAdd` is true; delete the `LOGGING TO` header at `FoodTab.tsx:761-781`; keep one search field seeded via `seedQuery`. → `/impeccable distill`

### [P1] Delete sits at the thumb-rest edge of every row, unconfirmed — and its Undo rewrites provenance

(a) Every row ends `⧉` · 1px divider · `✕`, both 44×44, **5px apart**, `✕` outermost — 20 glyph buttons down the outer right edge of a ~580px list. No confirmation. (b) `removeEntry` (`app/page.tsx:707`) undoes by re-creating via `api.createEntry`, whose payload omits `source`; `app/api/entries/route.ts:59` hardcodes `source: "ui"`; `lib/api-client.ts:124` omits `source` from the create type. `lib/validation.ts:183` accepts `"ui" | "mcp"` — the route overrides it.

Deleting an assistant row then tapping Undo silently converts it to user-typed. Breaks PRODUCT.md Principle 2 and DESIGN.md's "Don't drop provenance on a re-log". Copy-and-re-log degrades the same way.

**Fix.** Move delete into the existing `⋯` menu, or require a confirming second tap. Accept optional `source` on `POST /api/entries` for re-creation; pass `doomed.source` in both Undo handlers. → `/impeccable harden`

### [P1] Over-goal is carried by hue alone, and the bar stops measuring when it gets interesting

`Meter.tsx` expresses "over" via figure colour and fill colour only. `pct = goal ? Math.min(100, (value / goal) * 100) : 0` — 165/150 and 300/150 render identically. Track is `aria-hidden="true"`, no `role="progressbar"`, no `aria-valuenow`.

WCAG 1.4.1 failure (colour as sole means) on core content. Note this is *not* a contrast failure — the palette measured clean, so contrast testing would never catch it. The calorie readout owns the right vocabulary (`57 left` / `over`); the six meters have no word at all.

**Fix.** Append `+15g over` in `--over` using the existing annotation style; render overage as a distinct segment past 100% rather than clamping. Decide whether sugar and sodium are ceilings needing different fill grammar. → `/impeccable colorize`

### [P2] Row dividers are hardcoded `#e5e7eb` and are the brightest lines in the dark theme

`FoodTab.tsx:979` is `divide-y` with the colour set inline on the parent. `border-color` is not inherited and `divide-y` sets only `border-top-width` on children, so they fall through to Tailwind preflight `border: 0 solid #e5e7eb` (no `borderColor.DEFAULT` in `tailwind.config.ts`). Measured in the running app, dark: divider `#e5e7eb` = **14.5:1** vs panel; intended `--line-soft` `#1a2029` ≈ 1.07:1; panel border `#222a35`.

Ten sites: `AddFood.tsx:1487`, `WeightCard.tsx:232`, `ProductsCard.tsx:126`, `ShortcutsModal.tsx:36`, `DayLoadingSkeleton.tsx:65`, `ExerciseHistoryModal.tsx:229`, three in the workout tree.

Hierarchy inverted on the declared home ground. Breaks the Two-Value Rule and "Don't hardcode a hex". Detector cannot see it — the hex isn't in source.

**Fix.** `borderColor: { DEFAULT: "var(--line)" }` under `theme.extend`; replace each `divide-y` + parent-inline-colour pair with `divide-y divide-line-soft`. → `/impeccable polish`
